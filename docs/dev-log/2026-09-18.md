## 4. 重要な設計判断と、その理由（なぜそうしたか）

1. **マルチアカウント / クロスアカウント構成**
   - devにリソース、管理アカウントにDNS。providerを2つ定義し、management側は `assume_role`（TerraformRoute53CrossAccountRole）で操作。
   - ローカルもCIも同じコードで動くよう、profileは `dev_account_profile` 変数で切替（CIでは空文字を渡してOIDCのアンビエント認証を使う）。

2. **リソース名にランダムサフィックス（random_id）**
   - S3バケット名・OAC名の「AlreadyExists」衝突を根絶するため。作り直しでハマった教訓から導入。

3. **CI用IAMロールを bootstrap/ に分離（別ステート・手元管理）**
   - CIが自分自身のIAM権限を書き換えられる状態＝権限昇格リスクを排除するため。
   - アプリインフラ(../)のTerraformからはIAMを外し、CIのapplyはIAMを触らない。

4. **CloudFront Function でディレクトリindex解決**
   - Astroは `/about/` → `/about/index.html` を出力するが、OAC経由S3はindex自動解決しないため、`viewer-request` でURI書き換え。
   - 併せて、SPA用の `403→index.html` フォールバックを廃止（MPAには不適切だった）。

5. **OIDCの sub 条件**（ハマりポイント・重要）
   - GitHubの新仕様で sub が `repo:makotonic999@<ownerID>/DIVE@<repoID>:ref:...` の形式（名前直後に @数値ID）。
   - 信頼ポリシーは `repo:makotonic999*/DIVE*:*` でワイルドカード吸収。CloudTrailで実トークンを確認して確定した。
   - 併せて `sts:TagSession` も許可（configure-aws-credentialsのセッションタグ対応）。

## 5. 運用手順

### デプロイ（通常）
- **`main` に push するだけ**でGitHub Actionsが自動デプロイ（推奨）。

### 手動デプロイ（必要時）
```powershell
aws sso login --profile dev
cd C:\Users\HP\DIVE
.\scripts\deploy.ps1   # terraform outputから宛先取得 → build → S3同期 → invalidation
```

### Terraformをローカルで操作する時
```powershell
aws sso login --profile dev
aws sso login --profile management   # DNS(management)を触る場合
cd C:\Users\HP\DIVE\terraform
terraform plan    # 変更確認
terraform apply
```
- bootstrap（IAM）を変える時のみ `cd terraform\bootstrap` で別途 init/apply。

### 環境メモ
- Node.js は `C:\Program Files\nodejs`。素のPowerShellではPATHが通っていないことがある（deploy.ps1は内部でPATHを補う）。
- `npm run build` 前に手動で通すなら: `$env:Path = "C:\Program Files\nodejs;$env:Path"`
